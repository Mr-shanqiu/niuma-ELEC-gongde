# 站点归档与构建产物保留策略

本文只定义判断依据和清单口径，**不是删除授权**。任何实际删除都要按第 4 节单独确认，且不在本文范围内。

## 1. 现状盘点（2026-10-21 只读）

| 项 | 数值 |
| --- | --- |
| `dist/gongde-deploy/*.tar.gz` | 101 份，合计约 1.79 GiB |
| 被 `.local-work/` 回执或 `docs/` 引用的归档 | 66 份 |
| 未被任何回执/文档引用的归档 | 35 份 |
| 当前线上静态站 tree | `b9acc5a9…`（见 `PROJECT_HANDOFF.zh-CN.md`） |

"未被引用"不等于"无用"：引用只说明有人写下过这个摘要，不说明没有其他依赖。回退路径、CDN 缓存键、验收证据链都可能引用旧归档而没有留下可 grep 的文字。

PNG 口径同样需要标明：对 git 跟踪的全部 182 份 PNG 计算字节哈希，得到 65 组重复、80 份额外副本，额外副本合计 23,756,011 字节。重复字节不等于无用副本——客户端打包资源、形象源包、稳定兼容路径、内容寻址静态资源可能有意保留相同图片。去重不能破坏包签名、manifest/source-map 哈希、页面路径和旧 runtime 引用。

## 2. 保留类别

任何清理前，先把每个对象归入以下一类；归不进去的，保留。

1. **正式签名客户端**：已发布或已送签的安装包本体。永不因"旧版本"删除；摘要已进入发布回执和公开清单。
2. **当前站点及必要回退**：线上 tree 对应的归档，以及回退窗口内要用的上一版。回退窗口由发布节奏决定，不由文件时间决定。
3. **冻结验收与历史交易依据**：`.local-work/acceptance/`、`.local-work/candidates/` 中被回执引用的产物。这些是"当时确实这样做过"的唯一证据，删掉就无法重建。
4. **源素材**：可重新生成站点/形象包的输入（`website/`、`assets/`、`imports/` 之外的源）。不因"能从源码重建"而删除——重建得到的是新产物，不是当时发布的那一份。
5. **可重建缓存**：预览图、临时 staging、`build-*` 目录。只有这一类可以按"能重建"处理。

## 3. 判断规则

- 时间不是依据。`ls -t | head -3` 会删掉正在被引用的旧归档，也会留下没人用的新归档。
- 摘要相等不是合并依据。两个归档 tree 相同意味着内容相同，但删除哪一份取决于哪一份被引用，不取决于大小。
- 删除前必须能回答"这份被谁引用"。答案可以是"当前线上"、"回执 X"、"回退窗口"，不能是"看起来旧"。
- 客户端安装包不适用本文的清理流程。`services/gongde-payments/src/admin/object-store.ts` 已对 installer 删除强制抛 `installer_retention_required`，本地也不应绕过这条规则。

## 4. 实际清理的前置条件

若要真正清理，需要单独一轮明确授权，并且至少满足：

1. 生成逐文件清单（路径、字节、tree 摘要、引用来源、归类），供人工确认；
2. 确认回退窗口内没有任何归档被移除；
3. 确认没有 CDN 缓存键、manifest 或验收回执指向被移除对象；
4. 先移动而不是直接删除，保留一个可恢复的观察期；
5. 清理后重新盘点数量与字节，与本文口径对照。

本轮（2026-10-21）不删除、不移动、不改冻结摘要。
